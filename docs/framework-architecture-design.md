# IATest 框架总体设计方案（v4）

> 本文档是 IATest 的总体架构基线。上下文与经验库的详细设计见
> [context-system-design.md](context-system-design.md)，测试用例最终格式见
> [case-format-spec.md](case-format-spec.md)。

## 1. 设计目标

IATest 对大模型的使用遵循“模型负责语义判断，代码负责确定性转换和执行”的原则：

1. 大模型只在业务语义、场景设计、证据归因和冲突判断等非确定性环节工作。
2. 用例编号、默认请求、格式标准化、风险限制、覆盖验收和数据落库由框架执行。
3. 每个模型会话都有明确身份、最小工具权限、Token/轮次预算和质量门禁。
4. 上下文按需检索，避免在多个调用和批次中反复传递完整接口、用例及经验数据。
5. Web、CLI 和未来 API 共享同一应用命令、任务状态与审计数据。
6. 每次模型及工具调用均可追踪、可复现、可衡量，并支持失败恢复和局部修订。

## 2. 总体架构

框架采用六层结构。原身份层、工具层、数据层、交互层继续保留，新增编排运行层和领域契约层。

```text
Web / CLI / API
       │
       ▼
应用编排与 Agent Runtime
   ├── 身份与策略 RoleSpec
   ├── 模型网关 ModelGateway
   └── 工具注册表 ToolRegistry
              │
              ▼
      领域编译器与校验器
              │
              ▼
      数据仓库与外部适配器
```

依赖方向必须保持单向：

```text
交互层 → 应用/编排层 → 身份层、工具层 → 领域层 → 数据层
                         └──────────→ 模型网关
```

- 身份定义不读取数据库、不调用 Provider，也不依赖 Web/CLI。
- 工具只能通过受控上下文访问当前项目数据，不向模型暴露脚本路径或任意代码执行能力。
- 数据层不知道模型、Prompt 和页面。
- Web/CLI 不直接拼 Prompt，不直接解析模型结果。

## 3. 身份层

### 3.1 RoleSpec

身份不仅是一段 Prompt，而是可版本化的完整策略：

```yaml
id: case_designer
version: "1.3"
mission: 根据覆盖计划、接口事实和已确认经验设计测试场景
model_role: case_generator
input_contract: CaseDesignTask
output_contract: ScenarioDraft[]
allowed_tools:
  - list_endpoints
  - get_endpoint_detail
  - get_generation_strategies
  - search_confirmed_lessons
  - submit_case_drafts
forbidden_actions:
  - analyze_execution_results
  - execute_cases
  - write_project_data
max_tool_rounds: 10
max_tool_calls: 20
token_budget: 32000
```

RoleSpec 必须包含：

- 身份、目标、职责和明确禁止事项。
- 输入契约、语义输出契约和完成标准。
- 可用工具白名单。
- Token、轮次、工具调用次数和超时预算。
- 失败、降级、人工确认及质量门禁策略。
- 版本号，保证历史任务可以追溯当时的身份定义。

动态接口、用例和经验数据不得写入身份文件，应由工具按需访问。

### 3.2 内置角色

| 角色 | 职责 | 禁止事项 | 默认模型绑定 |
|---|---|---|---|
| `api_analyst` | 接口识别、接口语义补全、依赖候选分析 | 生成用例、执行用例、分析报告 | `master` |
| `test_planner` | 制定覆盖计划 | 生成最终 TestCase、保存数据 | `case_generator` |
| `case_designer` | 生成 ScenarioDraft | 分析执行报告、执行或保存用例 | `case_generator` |
| `case_maintainer` | 按接口变更或质量问题更新/退役指定用例 | 修改范围外用例、伪造替代接口 | `case_generator` |
| `result_analyst` | 基于执行证据归因和总结 | 修改用例、执行请求 | `analyzer` |
| `quality_reviewer` | 独立审查交付物的可靠性、完整性、合理性和非冗余性 | 修改产物、继承产出身份或读取产出会话历史 | 当前唯一审计模型（独立会话） |
| `context_curator` | 审查经验候选 | 未经门禁直接激活低置信度经验 | `master` |

角色解析必须 fail closed：未知角色直接报错，不得静默回退成主控角色。角色和模型配置解耦；专用模型未配置时可以按显式策略复用模型连接，但不能获得被复用角色的权限。

## 4. 领域契约层

### 4.1 可信接口契约

接口识别的交付物不是 method/path 列表，而是后续阶段唯一可使用的可信接口契约。契约包含 Endpoint 的参数、
请求体、响应 Schema、约束、依赖关系和结构化 `business_rules`。每条可测试业务规则至少包含：

```json
{
  "rule_id": "BR-...",
  "version": "1",
  "title": "不传 prefix 时随机生成 8 位邮箱前缀",
  "category": "behavior",
  "strategy": "optional_field",
  "testable": true,
  "lifecycle_state": "",
  "trigger": {
    "request_overrides": {},
    "omit_fields": ["query.prefix"],
    "chain_steps": []
  },
  "expected": {
    "status": 200,
    "basis": "responses.200",
    "assertions": []
  },
  "runnable": true,
  "risk": "",
  "fixture_requirements": [],
  "source_section": "生成临时邮箱 > 业务说明",
  "source_evidence": "..."
}
```

接口识别模型必须读取原始接口文档并保留业务条件、输入分区、生命周期状态、字段断言义务和夹具要求。框架以
确定性解析结果为 method/path 和可证明规则的下限，按字段合并模型语义补充，不能用章节标题、空参数列表或
简略描述覆盖更完整的来源事实。同一状态码下的非法字符、超长、重复参数、受限内容等输入类别必须保留为不同规则，
不能因为期望状态相同而合并。

原始文档的规范化快照只保存于 `api_docs/source-snapshot.md`，仅供接口识别编排阶段进行上游修订。用例规划、
用例设计和用例质量审计没有读取原文的工具权限，只能读取已审计 Endpoint 和 `business_rules`。用例生成预检若发现
接口缺失、规则缺失或契约哈希不一致，由编排器自动退回接口识别阶段携带缺口重新识别和审计；修复后再以新的接口产物
继续生成，不允许下游模型绕过接口识别自行查原文补事实。用户手动维护的接口目录以 `trusted_manual` 明确标记，
不会被后台自动重新添加已由用户删除的接口。

每份可信契约携带 `contract_version`、`contract_hash`、`contract_status`、
`source_snapshot_sha256` 和 `business_rule_count`。这些字段参与生成缓存指纹，契约或编译流水线变化后旧缓存立即失效。

### 4.2 语义中间契约

模型不再直接生成带全部标准字段的 TestCase，而是生成 ScenarioDraft：

```json
{
  "scenario_id": "SCN-USER-001",
  "endpoint_method": "POST",
  "endpoint_path": "/users",
  "intent": "验证缺少必填手机号时的处理",
  "design_method": "required_field",
  "priority_hint": "P1",
  "coverage_tags": ["required_field"],
  "request_overrides": {},
  "omit_fields": ["body.phone"],
  "expected_outcome": "返回接口文档声明的参数校验错误",
  "expected_basis": "responses.400",
  "assertions": [],
  "chain_steps": []
}
```

模型负责：

- 场景意图、业务条件、等价类、边界及异常设计。
- 预期结果语义和证据来源。
- 覆盖标签及必要的数据依赖描述。

领域编译器负责：

- 用例 ID、模块、标题、优先级、标签和设计方法标准化。
- 根据 Endpoint Schema 生成默认 headers/path/query/body。
- 应用字段覆盖、字段删除和链路步骤。
- 生成断言、preconditions、test_steps、setup_steps、cleanup_steps。
- 判定 negative、runnable 和 risk。
- 输出并校验最终 TestCase。

领域编译器还负责吸收不同模型的常见断言方言。例如模型输出的
`json_field_exists`，以及使用 `path`、`assertion`、`pattern` 字段的 `json_path`
断言，必须在本地转换为统一的 `target/operator/expected` 结构。该转换是确定性的，
不能为了字段改名再次调用模型；无法安全转换时才进入语义修订流程。

### 4.3 质量门禁

以下门禁由框架强制执行，模型无权跳过：

1. Endpoint 和链路步骤必须引用真实接口。
2. 接口识别必须覆盖本地解析器从同一文档提取出的 method/path 清单；模型可分批提交并补充接口，
   但不得以不完整列表结束任务或覆盖完整的确定性结果。
3. 每个计划场景必须且只能对应一个草稿和一个最终用例。
4. expected_outcome 不得为空；文档依据存在时 expected_basis 必须可定位。
5. status_code_coverage 不得产生文档未声明的状态码。
6. setup/steps/cleanup 的模板变量必须存在生产来源。
7. 不安全的破坏性或外部状态依赖用例不得被标记为可直接执行。
8. 最终 TestCase 必须通过统一格式规范和去重校验。
9. 每条可测试 `rule_id` 必须在 `coverage-manifest.json` 中关联至少一个用例；当前环境不能安全构造的规则必须以
   `fixture_required` 契约用例交付，不能静默遗漏或伪造请求。
10. 声明覆盖规则的用例必须在主请求或链路步骤中实现该规则的全部断言义务；仅在标题、预期结果或标签中提到规则
    不算覆盖。
11. 可信计划中的 method/path、触发请求差量、字段省略、断言、rule_ids、runnable 和夹具要求是不可漂移字段；
    模型草稿与其冲突时由框架以可信计划为准。

本地确定性门禁与多模型质量审计是两道不同的准入关：

- 本地门禁用于发现可由代码证明的结构、引用、变量流和契约错误；不通过时不浪费模型调用。
- 多模型审计用于评估必须结合语义和证据判断的质量；审计模型不能覆盖本地事实或直接修改产物。
- 只有同时通过两道门禁的候选才属于“质量审计通过”；三轮仍未通过时只能选择通过本地硬门禁、
  审计完整且没有 critical 问题的最高分候选，否则执行产物类型对应的安全兜底。

## 5. 工具层

### 5.1 ToolSpec

每个工具必须声明：

- 名称、用途、输入 JSON Schema 和输出说明。
- 允许的角色和副作用等级。
- 超时、结果大小、幂等性和是否为终止工具。
- 处理函数版本及审计要求。

工具副作用分级：

| 等级 | 示例 | 调用策略 |
|---|---|---|
| `read` | 查询接口、策略、经验 | 模型可在角色白名单内选择 |
| `transform` | 提交草稿、编译、覆盖检查 | 模型可提交，编排器强制编译和校验 |
| `write` | 保存用例、修改经验 | 仅编排器通过门禁后调用 |
| `execute` | 执行接口、验证依赖 | 编排器控制，按风险要求人工确认 |

内置读取工具：

- `list_endpoints`：分页返回接口摘要，不返回完整 Schema。
- `get_endpoint_detail`：按 method/path 返回单个接口详情。
- `list_business_rules`：分页返回接口识别产物中的结构化业务规则。
- `get_business_rule_detail`：按稳定 rule_id 返回触发条件、断言义务、生命周期和夹具要求。
- `list_existing_cases`：分页返回已有用例摘要，用于去重与维护定位。
- `get_existing_case_detail`：按用例 ID 返回单条完整用例。
- `get_generation_strategies`：返回本任务启用的策略。
- `search_confirmed_lessons`：仅查询符合注入门槛的经验。
- `get_dependency_graph`：返回已验证或项目元数据中的依赖关系。

终止工具：

- `submit_coverage_plan`：提交覆盖计划语义产物。
- `submit_case_drafts`：提交 ScenarioDraft 语义产物。
- `submit_case_maintenance`：提交逐项 `update|retire` 决策，update 必须携带 ScenarioDraft。
- `submit_endpoint_drafts`、`submit_dependency_graph`：提交接口识别和依赖分析产物。
- `submit_result_analysis`、`submit_result_review`：提交报告分析和失败复核产物。
- `submit_quality_review`、`submit_context_decisions`、`submit_conflict_reviews`：提交治理裁决。

保存、执行和任意文件/命令能力不对模型开放。

## 6. 编排运行层

Agent Runtime 负责：

1. 根据应用任务选择 RoleSpec 和模型连接。
2. 注入身份 Prompt、最小任务说明和该角色的工具定义。
3. 执行有界的“模型 → 工具 → 模型”循环。
4. 校验工具白名单、输入 Schema、结果大小和调用预算。
5. 对终止工具的语义产物执行领域编译与质量门禁。
6. 只把校验差量返回模型进行局部修订，不重发无关数据。
7. 保存运行、轮次、工具调用、Token、Prompt/产物哈希和错误。
8. 将任务目标、已完成动作、运行状态和证据索引维护为结构化任务记忆。
9. 在上下文达到水位时保存检查点并自动重建消息，不要求人工清空会话后重试。

同一身份可以服务多个任务，但单次会话只开放“RoleSpec 工具白名单 ∩ 当前任务工具集”。例如
`api_analyst` 的接口识别会话只能提交 `submit_endpoint_drafts`，依赖分析会话只能提交
`submit_dependency_graph`；`result_analyst` 和 `context_curator` 的不同任务同样不能互相调用另一类终止工具。

模型网关统一返回：

```text
ModelResponse
  text
  tool_calls[]
  usage(input_tokens, output_tokens, total_tokens)
  finish_reason
  provider_metadata
```

模型配置声明 `supports_tools`、`supports_json_schema`、`supports_stream` 和 `context_window`。支持原生工具协议时使用 Provider 原生调用；不支持时使用受限的兼容信封，控制信封解析失败只允许一次协议重试，不使用大模型进行 JSON 修复。

默认预算：

- `test_planner`：最多 6 轮、20 次工具调用、24000 Token。
- `case_designer`：最多 10 轮、20 次工具调用、32000 Token；轮次用于必要的语义修订，不能代替本地格式转换。
- 单个工具结果默认最多 24000 字符，超出后分页或截断并返回摘要。

### 6.1 交付物多模型质量审计

接口信息、测试用例、最终测试报告和经验候选统一进入 `QualityAuditService`。审计池按真实模型连接去重，
不是按 `master/case_generator/analyzer` 配置角色计数：

```text
unique_model_key = lower(provider)
                 + normalize(base_url)
                 + lower(model)
```

同一个模型即使配置给多个角色也只投一票；不同配置角色指向同一 provider/base_url/model 时会在审计记录中保留
角色来源，但不会重复调用或重复计分。产出模型可以作为审计池成员，票权与其他模型相同，因为每次审计都会创建新的
`quality_reviewer` 身份和会话，只发送待审产物、事实证据、评分规则及必要工具，不携带产出身份、产出消息历史或
“这是你生成的”之类的来源提示。

四维分数和框架计算权重为：

| 维度 | 权重 | 核心判断 |
|---|---:|---|
| 可靠性 | 40% | 是否与接口文档、执行结果和不可变事实一致 |
| 完整性 | 30% | 必要接口、场景、断言、失败证据和经验字段是否缺失 |
| 合理性 | 20% | 标题、依赖、结论、归因和建议是否符合业务语义 |
| 非冗余性 | 10% | 是否存在重复接口、重复场景、重复结论或无价值内容 |

模型只提交四维原始分数、置信度、总结和带位置/证据/原因/建议的结构化问题，最终加权分由框架计算。
critical 问题必须同时包含可定位位置和事实证据；缺少任一项时自动降级为 high，避免无证据否决。

候选必须同时满足以下条件才通过：

1. 所有已配置的唯一模型均成功完成审计。
2. 等权平均总分严格高于 85。
3. 可靠性均分不低于 90，完整性均分不低于 85。
4. 模型总分最大差值不高于 15。
5. 不存在有证据的 critical 问题。

单个审计模型的传输、协议或结构错误会在当前产出轮内独立重试，默认最多尝试 2 次，不消耗产出修订轮数；
仍失败则本轮审计不完整，不能通过也不能作为安全兜底。相同产物、证据、规则版本和模型的已完成分数可复用，
但框架始终按当前权重重新计算总分。

每类产物最多执行三轮“产出 → 本地门禁 → 全模型审计”。未通过时将去重后的低分原因、位置、证据和修复建议
反馈给该任务的产出模型。用例问题能定位到 case_id、scenario_id 或 rule_id 时，框架调用 `case_maintainer`
只修订命中用例并原样保留其他候选；整体缺失或没有现有用例可修时才重新规划。第三轮仍未通过时，选择全部安全候选中分数最高者；
如果没有安全候选，则接口信息回退确定性解析结果、用例回退确定性标准覆盖、报告只保留框架事实报告、经验不写入库。

## 7. 数据层

数据通过仓库接口访问：

- `ConfigRepository`：模型配置、角色绑定、生成与执行策略。
- `EndpointRepository`：接口目录、详情、版本和元数据。
- `CaseRepository`：正式用例和修订结果。
- `ContextRepository`：经验、冲突、审核和验证状态。
- `RunRepository`：用例执行证据。
- `AgentRunRepository`：模型轮次、工具调用、Token 和语义产物。
- `QualityAuditRepository`：审计会话、每轮完整候选、硬门禁结果、每模型四维分数、问题证据、产出血缘和最终选择。
- `AgentRunRepository` 同时保存任务证据和上下文检查点；大对象退出 Prompt 后仍可按运行 ID 和证据 ID
  分页取回，模型不能读取其他运行的证据。

数据必须携带项目作用域、来源、时间、版本/快照、可信状态及生成者。SQLite 是运行时事实源；模型只获得查询工具返回的当前任务最小数据。

上下文采用分级加载：接口目录摘要 → 单接口详情 → 相关经验 → 必要执行证据。工具结果在后续轮次使用引用和哈希，避免反复内联相同大对象。

## 8. 交互层

### 8.1 模型交互

ModelGateway 屏蔽 OpenAI Compatible、Anthropic 等协议差异，负责消息、工具调用、流式响应、用量和结束原因转换。Provider 不负责任务角色和业务重试。

### 8.2 人机交互

Web、CLI 和 API 只提交应用命令并消费任务事件：

```text
TaskStarted → RoleSelected → ToolCalled → DraftSubmitted
→ CasesCompiled → QualityGatePassed → TaskCompleted
```

应用命令负责项目作用域和持久化边界。页面不拼 Prompt，CLI 不直接解析模型输出，后台任务可以从持久状态恢复。
Web 任务进度明确区分模型产出和质量审计阶段；配置中心展示最近审计会话，详情页按轮次展示本地门禁、
每个唯一模型的四维分数、扣分原因、证据、修复建议和最终交付候选。

## 9. 用例生成标准流程

1. 编排器先验收可信接口契约；发现上游缺口时自动退回接口识别阶段修订，规划和审计均不读取原始文档。
2. 框架根据接口 Schema、每条 `business_rule`、生成策略和依赖图在本地生成标准覆盖计划，包括主流程、必填/可选字段、
   等价类、边界、文档化状态码、生命周期、夹具场景和可证明的数据依赖链；模型计划与本地计划合并、去重。
3. 标准覆盖计划不再发送给 `case_designer`，直接由确定性编译器生成完整 TestCase 并附加 setup/cleanup。
4. 单请求且触发条件可证明的规则直接本地编译；跨接口状态变化等需要语义编排的规则按接口模块、依赖关系和场景数
   分批发送给 `case_designer`。缺少安全夹具的规则保留为不可执行契约用例，不发送猜测请求。
5. 模型按需读取最小接口详情并调用 `submit_case_drafts`，无需生成固定的最终文件格式。
6. 领域编译器统一不同模型的断言、状态码、变量提取和模板方言，再执行接口引用、请求契约、
   每步状态断言、跨步骤数据流、预期字段/值/空数组与实际断言一致性门禁。
7. 只把失败场景及错误差量发送给模型定向修订；修订后仍不闭环的可选模型增量被剔除并记录原因，
   不得阻断已经通过门禁的确定性标准覆盖。
8. 框架生成 `coverage-manifest.json`，验收所有可测试 rule_id 的处置、用例血缘和断言义务；最终用例再进入全部
   唯一模型的独立质量审计。未达标时优先定向维护命中用例，必要时才重新规划。
9. 通过审计或选出最高分安全候选后，在保存前和重新加载后各验收一次；只有问题数为零才更新正式产物。
10. 保存 AgentRun、工具调用、Token、流水线版本、角色版本、质量审计血缘和产物哈希。缓存键包含这些版本及接口、
   策略和依赖图哈希，旧流水线缓存不得复用。

多角色不代表固定增加产出模型调用次数。格式转换、默认值、去重和规则校验全部本地执行；四类正式交付物默认执行
全部唯一模型审计，确定性门禁失败的候选会在调用审计模型前被拒绝，以减少无效 Token。
单次会话开放的工具还应按具体任务进一步收窄：规划角色只获得规划工具，普通用例设计批次不获得已有用例、
全量策略和依赖图工具；只有补充生成、链路场景等确有需要的任务才追加对应工具。

## 10. 安全与治理

- 角色和工具采用白名单，未知角色、未知工具和越权工具均 fail closed。
- 工具参数在执行前按 Schema 校验，项目名和路径使用安全规范化。
- 密钥不进入 Prompt、工具结果和 Agent 审计库。
- 工具结果限制大小，审计库保存摘要、哈希和必要结构，不保存无限原始内容。
- 写入及执行工具必须幂等或明确标记不可重放。
- 网络执行、DELETE 及其他破坏性动作沿用人工确认和安全策略。
- 同项目识别、生成和执行使用跨进程操作锁；Web 后台任务使用有界工作池和持久状态，避免重复提交和线程无限增长。
- OpenAPI/文档输入、上传体积、HTTP 请求与响应留存、工具结果和审计字段均设上限；远程文档限制来源与重定向，禁止远程文件引用。
- Web 默认只监听回环地址，校验 Origin、项目名和接口表单，设置安全响应头并采用原子写入。
- Web 写操作页面为每个 POST 表单注入进程级 CSRF 令牌；精确同源和等价回环地址直接通过，反向代理或嵌入式预览
  造成 Origin/Host 不一致时凭令牌继续执行。拒绝和参数错误统一返回 UTF-8 响应，错误文本不得进入 HTTP 状态行。
- 每条并发用例获得进程内单调纳秒上下文值，setup/cleanup 不得因同毫秒前缀碰撞而操作其他用例资源。

## 11. 可观测性与验收指标

每次生成记录：

- 模型、角色及 RoleSpec 版本。
- 输入/输出/总 Token、调用次数、工具调用次数、延迟和错误。
- 草稿数量、编译成功率、门禁问题及局部修订次数。
- Prompt、上下文包、工具结果和最终产物哈希。

核心质量指标：

- 每条验收通过用例 Token。
- 首次语义产物可编译率和协议修复率。
- 幻觉接口率、重复率、计划兑现率。
- runnable/risk 误判率和变量流错误率。
- 人工修改比例、最终执行成功率和有效缺陷发现率。

仓库内的自包含合成契约是固定交付验收基线。每次变更先使用相同 Endpoint 和黄金断言验证编译、依赖准备、清理、覆盖门禁和持久审计；
涉及模型协议、Prompt、工具集、Agent 编排或接口执行的交付，还必须在不纳入版本库的受控环境中完成真实模型和真实接口验收。

## 12. 迁移与兼容策略

迁移按可独立交付的完整能力推进，当前基线已完成以下步骤：

1. 建立 ScenarioDraft、领域编译器和质量门禁。
2. 建立 RoleSpec、工具注册表和只读数据工具。
3. 扩展 ModelGateway，支持原生工具调用和用量协议。
4. 建立有预算、有状态、有审计的 Agent Runtime。
5. 将用例生成主链切换到新运行时；保留显式 legacy 开关用于短期回滚。
6. 迁移接口识别、报告分析和经验治理角色。
7. Web/CLI 统一使用应用命令和任务事件。

旧版 TestCase Markdown、已有 Provider 配置和现有项目数据格式保持兼容。旧 Prompt 和旧生成链只作为显式回滚路径，不能在新链失败时静默执行并掩盖错误。

- `test_planner` 对 5 个真实接口生成了 35 个计划场景，消耗 12569 Token。随后将 34 个场景一次性交给
  `case_designer` 时出现持续推理且未及时提交终止工具，证明仅按接口数分批不足。
- 改为同时按场景数分批后，4 场景真实设计成功生成并编译 4 条用例；进一步收窄任务工具集，避免普通设计批次

这些失败在开发阶段通过 Agent 审计库完成了 Provider 超时、批量过大和人工中止的原因定位；正式交付时按授权清理失败和悬挂记录。

### 13.6 接口维护与生成任务联调记录（2026-07-16）

  五批错误数由 `6/5/8/0/1` 降为 `0/0/0/0/0`，后续不再为这些格式差异调用修订模型。

### 13.7 用例语义一致性联调记录（2026-07-16）

- 接口用例默认请求改为只填充必填参数；可选参数必须由草稿明确指定。标题、意图或预期结果包含
  “不传/未传/省略”等语义时，编译器还会移除与该语义冲突的可选 Query 参数，避免模型未提供覆盖值时
  反而注入接口示例值。
- 断言规范化支持真实模型已返回的 `pattern`、`type_check`、`matcher`、`status`、`json`、
  `field_exists`、`field_type` 和 `field_value` 等方言。需要比较值的运算符若缺失 `expected`，
  编译阶段直接失败，不再生成 `eq null` 这类表面合法但语义错误的断言。
- 编译器依据接口响应 Schema 检查预期结果中明确提及的字段；缺失的字段断言会按显式常量或 Schema 类型
  确定性补齐。依赖链草稿同时规范化 `action=call/extract`、`${VAR}`、路径参数别名及链路方法，避免链路
  被误编译为单接口请求。
- 最终门禁不只检查草稿能否转成 TestCase，还会检查状态码是否来自文档、响应字段是否属于对应 Schema、
  预期字段/显式值/数组顺序是否有断言、必填路径参数是否仍是 Schema 占位值，以及 CHAIN 是否存在真实的
  `extract → template inject` 数据流。用例保存后还使用同一门禁重新加载验收，覆盖最终交付边界。
- HTTP Path、Query 和 Header 参数在线上传输时本质上都是字符串；对 Schema string 参数传入 Python 整数
  并不能形成真实的“类型错误”。覆盖计划不再自动添加这类伪用例，避免产生必然与真实请求矛盾的预期。
- 使用最新一次真实生成保存的 6 批原始草稿离线重放，原 35 条中剔除了 5 条无法在线上表达的伪类型错误
  场景，其余 30 条均一次编译通过；保存并重新加载后的全局门禁问题数为 0。`TC-API-0001` 当前请求不携带
  `prefix`，并校验邮箱格式、`expires_in=600` 和 `created_at` 整数类型。
- 对 `TC-API-0001` 执行真实接口验收：服务返回 200、随机 8 位邮箱前缀、`created_at` 时间戳和
  `expires_in=600`，全部断言及 DELETE 清理步骤通过。
- 进一步真实抽样执行 7 条不同语义的用例，覆盖可选参数、数组排序、普通依赖、续期、删除和四步主链路；
  7 条全部通过，断言错误为 0，需要清理的场景也全部清理成功。

### 13.9 Agent 上下文自动恢复（2026-07-29）

- 任务记忆不再等同于完整聊天记录。运行时持续维护任务目标、已完成工具调用、协议修正、领域状态、下一步动作和
  证据索引；原始任务与完整工具结果写入 `agent_evidence`，Prompt 只携带必要状态和证据引用。
- 输入占安全容量 55% 时先压缩较早的模型/工具文本；达到 70% 时自动写入 `agent_checkpoints`，并将消息重建为
  “原身份 System + 结构化任务检查点 User”。目标水位为 35%，自动恢复后再继续原任务。
- 上下文重建不重置本次运行累计 Token、工具次数或角色总预算。已经成功执行的幂等副作用工具按调用签名去重，
  防止恢复后重复保存、提交或修改数据。
- 所有身份只额外获得只读 `read_task_evidence` 工具，可凭当前运行内的证据 ID 分页恢复原文；证据查询受运行 ID
  隔离并统一脱敏，避免通过检查点泄露其他任务内容。
- 80% 是“自动重建后的熔断线”，不是首次越线即失败。只有重建后仍超线、同一任务已重建 3 次，或角色总 Token
  预算已经耗尽时才停止并给出明确原因；正常恢复无需人工介入。
- 用例详情的生成依据按当前用例主请求、setup、CHAIN 和 cleanup 涉及的接口筛选，只展示经验标题、内容、适用接口和状态；
  `les-*` 不再进入业务界面，Token 估算和 ContextPack 快照编号仅保留在折叠的技术审计区。
- 用例列表和详情均提供编辑、删除入口。编辑覆盖基本信息、请求、断言、准备/链路/清理步骤，保存前重新执行统一交付门禁；

### 外部测试能力与接口 Mock

- `fixtures.providers` 是确定性运行时扩展点，支持静态变量提供者和 HTTP 准备/清理提供者。
- 执行器仅在用例声明的全部外部能力均已启用且配置有效时解除跳过；准备结果注入模板上下文，清理在成功或失败后执行。
- 外部能力调用、变量提取和清理均由执行器完成，不依赖模型规划或工具调用。
- `iatest mock` 启动独立的配置驱动 HTTP 服务，支持条件路由、路径模板、响应序列、延迟和脱敏请求记录。
- Mock 只替代被测系统的上游依赖，不能拦截测试执行器对被测接口的请求，也不能参与断言裁决。
