# 上下文与知识治理

## 目的

上下文用于复用已确认的业务规则、断言经验、数据依赖和已知问题，减少重复生成错误预期。它是可审计的项目知识，不是把所有历史日志无差别注入模型。

## 存储与来源

实现位于 `iatest/context/`。每个项目使用 SQLite，保存知识条目、来源、关系、冲突、审核操作和 ContextPack。全文检索用于召回，生成的项目记忆是可重建视图，不作为唯一事实源。

知识记录包含项目范围、类别、正文、接口/路径绑定、环境、生命周期、审核状态和证据来源。来源与条目分开保存，相同知识可合并多个来源；导入时验证项目、结构和路径边界。

## 提取与确认

接口识别、生成、运行及结果分析产生候选知识。候选必须通过结构和内容约束，不能直接变成已确认业务规则。控制台提供确认、忽略、编辑、保留、合并和问题解决操作。

确定性去重优先使用规范化 exact key，再处理语义相似和矛盾。重复来源增加来源记录而不是重复条目；不能凭模型的相似判断直接覆盖不同环境或不同接口的规则。

## 冲突和生命周期

冲突条目保留双方内容及来源，由治理操作决定保留一项、都保留、合并或忽略。已知问题可形成解决候选，复发时恢复问题状态；一次通过不自动删除历史来源。数据依赖单独保留候选、验证和失效语义。

每次治理操作写审计记录。清理历史、导入和索引重建使用明确入口，不能绕过审核修改知识事实。

## 注入流程

1. 按当前项目、接口、路径和环境召回候选。
2. 排除审核/生命周期不允许的内容，标记冲突和不适用原因。
3. 合并可归组的数据依赖，按可信度、相关性和预算排序。
4. 在 Token 预算内生成上下文，并保留被采用和排除的条目及原因。
5. 保存 ContextPack，使生成和分析可追溯到具体来源。

预算使用估算而不是供应商账单。敏感原始值不进入可共享知识正文。框架不能从未确认经验推导新的授权或修改冻结的测试预期。

## 控制台和维护

「项目上下文」提供知识列表、搜索、冲突处理、来源、趋势及审计。「配置中心」控制注入、治理和保留策略。相关 CLI 可由 `iatest context --help` 查询。

接口覆盖、历史通过率与样本可比性分别计算。样本数量或执行范围变化时，不把表面通过率变化直接解释为服务回归。

实现依据：`context/storage.py`、`context/signatures.py`、`context/injection.py`、`application/governance.py`。
